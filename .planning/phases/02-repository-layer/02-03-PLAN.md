# Phase 2 Plan 03: Remaining Route SQL → Repositories

## Objective

Close out success criterion 1: after this plan, a grep for `db.get`/`db.all`/
`db.run` across the whole `app/` tree returns nothing. Plans 01 and 02 covered
the substrate and the project-scoped subtree; this plan takes the remaining
route families — portfolio, programs, operations, admin, jira, export, auth,
config.

This is the largest statement count of the three plans but the lowest risk per
statement: most are reads feeding dashboards and reports.

## Artifacts this phase produces

- `lib/repositories/portfolio.repo.ts` — portfolio rollups, roadmap, budgets, members, allocations, quota, milestones, bug assignees
- `lib/repositories/programs.repo.ts` — programs (DB table `customers`) + project allocations
- `lib/repositories/operations.repo.ts` — ops systems, budget items, expenses, incidents
- `lib/repositories/admin.repo.ts` — companies, users, rag-config, resource audit, demo requests
- `lib/repositories/jira-config.repo.ts` — `company_jira_config` reads/writes and jql presets
- `lib/repositories/settings.repo.ts` — the `settings` key/value table
- `lib/repositories/auth.repo.ts` — user lookup + session rows used by login/logout/me/change-password

<action>
Move SQL from the portfolio and programs route families into
`portfolio.repo.ts` and `programs.repo.ts`.

`app/api/portfolio/report/route.ts` holds 26 statements — read the whole file
before extracting. Several are correlated aggregate queries whose results feed
each other; moving them individually without following the data flow will
produce a repository of misnamed one-off queries. Name each function after what
it answers (`bugCountsByProject`, `spendByCategory`), not after the SQL shape.

Programs are the `customers` table with `customer_id` foreign keys. Keep the
dual naming: repository function names use the domain word "program", SQL keeps
`customers`. Do not rename the table.

These routes are company-scoped rather than project-scoped, so functions take
`companyId` explicitly, plus an `isAdmin` boolean where the current SQL branches
on admin (admin bypasses the company filter). Passing the resolved boolean keeps
the session out of the repository while preserving the branch.
</action>
<acceptance_criteria>
- `grep -rn "db\.\(get\|all\|run\)" app/api/portfolio app/api/programs` returns no matches
- `portfolio.repo.ts` function names describe results, not SQL verbs (no `select1`, `query2`)
- Neither new repo imports `@/lib/auth` or `next/server`
- `npx tsc --noEmit` exits 0
</acceptance_criteria>
</task>

<action>
Move SQL from operations, admin, jira-config, settings, and auth routes into
their repositories.

Two care points:

`lib/auth.ts` itself contains SQL for session lookup. It is a lib module, not a
route, so success criterion 1 does not require moving it — the criterion names
`route.ts`, service, and component files. Move only the SQL that lives in the
auth *routes* (`login`, `logout`, `change-password`, `complete-onboarding`)
into `auth.repo.ts`. Leave `lib/auth.ts` alone; refactoring the session
substrate is not this phase's goal and would ripple into every route at once.

`settings` and `company_jira_config` are the two tables `lib/db.ts`
`needsReturningId` explicitly excludes from `RETURNING id` because they lack a
serial `id`. Repository writes against them must not assume
`result.lastInsertRowid` is meaningful. Read that function before writing these
two repos.

`app/api/config/route.ts` POSTs into `settings` including the Anthropic API
key, and currently has no admin check. Moving its SQL does not fix that. Record
it in the phase summary as an open finding for Phase 5/6 rather than silently
leaving it or silently fixing it mid-refactor.
</action>

## Threat Model

ASVS L1. Block on: high.

| # | Threat | Severity | Mitigation |
|---|---|---|---|
| 1 | Extraction drops the `company_id` filter from a portfolio/admin read, exposing every tenant's rows to any authenticated user | **High** | Company-scoped repository functions take `companyId` and `isAdmin` explicitly; tests assert a non-admin caller sees only its own company's rows. |
| 2 | The admin bypass is inverted or widened during extraction, granting non-admins admin scope | **High** | A test asserts `isAdmin: true` sees all rows and `isAdmin: false` sees only its company's; the bypass is a parameter, never inferred inside the repository. |
| 3 | Repository reads the session to decide admin status, moving an authorization decision below the route layer | Medium | REPO-02/REPO-06: `grep` for `@/lib/auth` and `next/server` under `lib/repositories/` must return nothing. |
| 4 | The known missing admin check on `app/api/config/route.ts` is silently "fixed" here, mixing an authorization change into a refactor phase and hiding it from the Phase 5/6 rollout | Medium | Explicit prohibition: leave it unchanged, record it as an open finding in the summary so Phase 5/6 inherits it. |
| 5 | Tests run against the dev database and mutate real data | Medium | Reuse Phase 1 `test/db.ts` guardrails (`TEST_DATABASE_URL`, `_test` suffix required). |
