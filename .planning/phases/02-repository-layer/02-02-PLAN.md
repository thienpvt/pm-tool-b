# Phase 2 Plan 02: Project-Scoped Route SQL → Repositories

## Objective

Move every SQL statement in `app/api/projects/[id]/**/route.ts` into a
`lib/repositories/*.repo.ts` module. Plan 01 established the substrate
(`allowlist.ts`, the `.repo.ts` convention, and the 7 write allowlists);
this plan finishes the read paths and the remaining nested resources so that
no `db.get`/`db.all`/`db.run` call survives under `app/api/projects/`.

Scope is the project-scoped subtree only. Portfolio, operations, admin, jira,
and export routes are plan 03 — keeping them separate means each wave has a
grep that either returns clean or does not.

## Artifacts this phase produces

- `lib/repositories/activities.repo.ts` — `listByProject`, `create`, `update`, `remove`, `maxOrderIdx`
- `lib/repositories/risks.repo.ts` — `listByProject`, `countByProject`, `create`, `update`, `remove`
- `lib/repositories/issues.repo.ts` — same shape as risks
- `lib/repositories/meetings.repo.ts` — `listByProject`, `create`, `update`, `remove`
- `lib/repositories/team.repo.ts` — `listByProject`, `create`, `update`, `remove`
- `lib/repositories/escalations.repo.ts` — `listByProject`, `create`, `update`, `remove`
- `lib/repositories/milestones.repo.ts` — `listByProject`, `create`, `update`, `remove`, epic children
- `lib/repositories/bugs.repo.ts` — `listByProject`, `create`, `update`, `remove`
- `lib/repositories/documents.repo.ts` — `listByProject`, `create`, `remove`
- `lib/repositories/holidays.repo.ts` — `listByProject`, `create`, `remove`
- `lib/repositories/budget.repo.ts` — budget items + expenses, scoped by `projectId`

<action>
For each of the six resources, move the GET/POST SQL out of the route and into the
matching `.repo.ts` module alongside the update function plan 01 added.

Function signatures take resolved scoping params, never a request or session:
- `listByProject(projectId: number)` — returns rows in the route's current ORDER BY
  (`activities` orders by `order_idx, id`; `risks`/`issues` by `id`)
- `create(projectId: number, input: <Resource>Input)` — returns the created row
- `remove(projectId: number, rowId: number)` — returns `{ changes: number }`

Preserve exact current behavior, including quirks:
- `activities.create` computes `maxOrderIdx(projectId) + 1` for `order_idx`, and
  falls back to the project's own `status` for `project_status` when the body
  omits it. That cross-table read moves into `activities.repo.ts` as
  `projectStatus(projectId)` — it is SQL, so it belongs behind the repository.
- `risks.create` and `issues.create` derive the display id (`R{n}` / `I{n}`)
  from `COUNT(*)` when the body omits it. Keep the same count-based derivation;
  do not "improve" it to a sequence, which would change assigned ids.
- The `db.get('SELECT * FROM x WHERE id = ?')` re-read after each write stays —
  routes return the persisted row, and callers depend on that shape.

Routes keep their DELETE `rowId`-from-querystring parsing and their existing
auth posture. This plan moves SQL only; it does not add authorization — that is
Phase 5/6 by design, and pretending otherwise here would hide the gap.
</action>
<acceptance_criteria>
- `grep -rn "db\.\(get\|all\|run\)" app/api/projects/\[id\]/{activities,risks,issues,meetings,team,escalations}/route.ts` returns no matches
- Each of the six `.repo.ts` files contains `from '@/lib/db'` and no `next/server` import
- `npx tsc --noEmit` exits 0
</acceptance_criteria>
</task>

## Threat Model

ASVS L1. Block on: high.

| # | Threat | Severity | Mitigation |
|---|---|---|---|
| 1 | Extraction drops the `AND project_id = ?` guard from an UPDATE/DELETE, letting a caller mutate another project's row by id alone | **High** | Every extracted write keeps `project_id` in its WHERE clause; each repository test asserts a row from project B is unaffected by a write scoped to project A. |
| 2 | A repository silently widens a read by omitting `project_id` from the WHERE clause, leaking cross-project rows | **High** | `listByProject` tests seed two projects and assert the other project's rows are absent. |
| 3 | Repository starts resolving its own scoping (reading session) so route-level access checks become bypassable | Medium | REPO-02/REPO-06: `grep` for `@/lib/auth` and `next/server` under `lib/repositories/` must return nothing. |
| 4 | Tests run against the dev database and mutate real data | Medium | Reuse Phase 1 `test/db.ts` — `TEST_DATABASE_URL` only, refuses a database whose name does not end in `_test`, never calls `getDb()`. |
| 5 | Behavior drift in derived values (order_idx, display ids) changes what is persisted | Low | Tracked as backstop truths; verified by test plus `next build` and full suite. |
