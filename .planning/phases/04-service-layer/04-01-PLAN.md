# Phase 4 Plan 01: Service Substrate + Reference Service

## Objective

Build the three pieces every other Phase 4 plan depends on — typed errors, the ownership
assert, and the route-level error mapper — then prove them end to end by converting one
real resource. `risks` is the reference because it is a pure pass-through today with **no
session check at all**, so converting it exercises both halves of the phase: extraction and
the new 403.

This is the tracer slice. Nothing in waves 2 or 3 starts until this is green.

## Context

`lib/services/` does not exist. Two file-private access helpers exist and **diverge**:

- `app/api/projects/[id]/route.ts:8-18` — `checkAccess`, correctly distinguishes 401 / 404 / 403
- `app/api/projects/[id]/budget/route.ts:14-22` — `checkBudgetAccess`, collapses all three to 401

CONTEXT locks the unified semantics on `checkAccess`'s shape: 401 only for a missing session,
404 for a missing project, 403 for cross-company. The budget divergence is corrected in wave 3
and is an intentional HYG-02 behavior change.

`projectAccessRow(projectId)` (`lib/repositories/projects.repo.ts:36`) returns
`{ company_id, customer_company_id }` or `undefined`. It is the ownership primitive — the
service assert wraps it, and no service re-implements the query.

`ValidationError`. Each extends `Error`, sets `this.name` to its own class name, and carries
**no** `status` field.

<task id="04-01-02" type="tdd">
<action>
Create `lib/services/access.ts` exporting `assertProjectAccess(projectId, actor)` where
`actor` is `{ company_id: number | null; is_admin: number | boolean }` — a plain object, never
a `NextRequest`. The route resolves the session and passes these two fields.

Semantics, in this exact order:
1. If `actor.is_admin` is truthy → return immediately, no ownership query.
2. Call `projectAccessRow(projectId)`. If it returns undefined → throw `NotFoundError`.
3. If `actor.company_id` is not null → allow when `row.company_id === actor.company_id` OR
   `row.customer_company_id === actor.company_id`; otherwise throw `ForbiddenError`.
4. If `actor.company_id` IS null → allow ONLY when `row.company_id === null` AND
   `row.customer_company_id === null`. This mirrors the CR-01 predicate in
   `listProjects` (`lib/repositories/projects.repo.ts:73-76`) — a null-company user must not
   match a real tenant's project. Otherwise throw `ForbiddenError`.

The function returns `void` on success and throws on failure. It must not return a boolean —
a forgotten `if` on a boolean return is exactly the failure mode this phase exists to prevent.

Write tests first covering all five paths: admin bypass (asserting `projectAccessRow` is never
called), missing project, owner via `company_id`, owner via `customer_company_id`,
cross-company denial, and both null-company branches (unassigned project allowed, assigned
project denied).
</action>

<task id="04-01-03" type="tdd">
<action>
Add `serviceErrorResponse(e: unknown)` to `lib/api-errors.ts`, alongside the existing
`repoErrorResponse` and `integrationErrorResponse`. Map `ForbiddenError` → 403,
`NotFoundError` → 404, `ValidationError` → 400. For any other error, `console.error` it
server-side and return the generic `{ error: 'Internal server error' }` at 500 — never
`String(e)`.

Response bodies: `{ error: 'Forbidden' }`, `{ error: 'Not found' }`, and for ValidationError
`{ error: <message>, field?: <field> }`. The Forbidden body must not include the message —
it could name a resource the caller cannot see.

Critically: `serviceErrorResponse` must NOT swallow `IntegrationError`. A service that wraps
an integration call re-throws it untouched (CONTEXT decision), so routes that can produce one
call `integrationErrorResponse` in the same catch. Add a test proving an `IntegrationError`
passed to `serviceErrorResponse` falls through to the generic 500 rather than being
misclassified — this documents the boundary.

Follow the file's existing comment convention explaining why mappers live outside the layers
that throw.
</action>
