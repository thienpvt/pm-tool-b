# Phase 6 Plan 03: Convert the 3 projects/[id] Report Routes

## Objective

Convert the 3 `app/api/projects/[id]/**` report routes that Phase 5 did NOT reach
(`report`, `project-report`, `project-report/generate-email`) onto `withProjectAccess`,
closing ROUTE-03's "every route under projects/[id]/**" and adding the 401/403 test coverage
(ROUTE-09, ROUTE-10) these routes lack entirely.

These are behavior-freeze conversions: the ownership check these routes need is the same
`assertProjectAccess` the wrapper's `withProjectAccess` already calls through the services
Phase 4 extracted. The POST handlers' `force500` AI integration-error mapping is PHASE-3 frozen
and must survive the wrap byte-for-byte.

## Context

The 21 `projects/[id]/**` routes: 18 wrapped in Phase 5 wave 2. The 3 stragglers are the report
routes, each with a `report.service.ts`/`project-report.service.ts` behind them (Phase 4). Their
GET handlers are heavy aggregates (report/generate) and their POSTs are AI report-generation
handlers calling the Phase 3 Anthropic client with `integrationErrorResponse(e, { force500: true })`.

These are project-scoped (they take a project id and return that project's report) — the wrap
target is `withProjectAccess`, NOT the plain `withAuth`.

No test files exist for any of the three. The route-test template is
`app/api/projects/[id]/risks/route.test.ts` + the access-focused
`route.access.test.ts` convention.
