# Phase 2 Plan 01: Kill Mass Assignment

## Objective

Close the 7 mass-assignment write paths by moving them behind repositories with
explicit per-resource column allowlists. This is the live tenant-isolation hole
(a client can currently `PATCH` `company_id` onto another tenant), so it goes
first — before the bulk read migration in Plans 02/03.

Scope is exactly the 7 files that build `SET` clauses from `Object.keys(body)`,
confirmed by grep:

| Route | Table | Current shape |
|---|---|---|
| `projects/[id]` PATCH | `projects` | `Object.keys(body)` — no `id` strip |
| `projects/[id]/activities` PUT | `activities` | `{id: rowId, ...fields}` |
| `projects/[id]/risks` PUT | `risks` | `{id: rowId, ...fields}` |
| `projects/[id]/issues` PUT | `issues` | `{id: rowId, ...fields}` |
| `projects/[id]/meetings` PUT | `meetings` | `{id: rowId, ...fields}` |
| `projects/[id]/team` PUT | `team_members` | `{id: rowId, ...fields}` |
| `projects/[id]/escalations` PUT | `escalation_levels` | `{id: rowId, ...fields}` |

<task id="1" type="execute">
<objective>Shared update builder that rejects unknown columns</objective>
<read_first>
- `lib/db.ts` (lines 1–55 — `DbClient` interface and `toPositional`; the `?` placeholder convention is mandatory)
- `test/db.ts` (the `TEST_DATABASE_URL`-only pattern from Phase 1)
</read_first>
<action>
Create `lib/repositories/_helpers.ts` exporting:

- `class UnknownColumnError extends Error` with a `columns: string[]` field, message `Unknown column(s): a, b`.
- `buildUpdate(table: string, allowlist: readonly string[], fields: Record<string, unknown>): { sql: string; values: unknown[] }`

`buildUpdate` behavior:
- Reject: any key of `fields` not in `allowlist` throws `UnknownColumnError` listing every offending key (not just the first). Rejection, never silent drop — REPO-03.
- Empty `fields`, or `fields` with every key filtered out, throws `UnknownColumnError` with an empty `columns` array and message `No updatable columns provided` (an empty `SET` clause is invalid SQL).
- Returns `sql` as the `SET` fragment only (`col = ?, col2 = ?`) using `?` placeholders in `allowlist` order — not caller-key order, so output is deterministic.
- Table name is interpolated by the caller into its own statement; `buildUpdate` does not build the full statement and never interpolates a value.
</action>
<acceptance_criteria>
- `lib/repositories/_helpers.ts` exports `buildUpdate` and `UnknownColumnError`
- `buildUpdate('projects', ['name'], {name: 'x'})` returns `{sql: 'name = ?', values: ['x']}`
- `buildUpdate('projects', ['name'], {company_id: 9})` throws `UnknownColumnError` with `columns: ['company_id']`
- `buildUpdate('projects', ['name'], {company_id: 9, tenant: 1})` throws with both keys in `columns`
- `buildUpdate('projects', ['name'], {})` throws `UnknownColumnError`
- `_helpers.ts` imports nothing from `next/server`, `@/lib/auth`, or any service
</acceptance_criteria>
</task>

## Threat Model

| # | Threat | Severity | Mitigation |
|---|---|---|---|
| 1 | Client sets `company_id`/`customer_id` via PATCH, moving a project across tenants | **High** | Both excluded from `PROJECT_COLUMNS`; rejected with 400. This is the plan's primary purpose. |
| 2 | SQL injection through a column key interpolated into `SET` | **High** | Keys are matched against a static allowlist before any interpolation; values stay parameterized. |
| 3 | An allowlist derived from CREATE TABLE alone silently stops persisting migration-added columns | Medium | Task 2 diffs against migration-added columns and the live write paths; REPO-04 record is the artifact. |
| 4 | Repository tests hit the real database and run `seedAuthData` default credentials | Medium | Reuse the Phase 1 `test/db.ts` helper: `TEST_DATABASE_URL` only, refuse non-`_test` names, never call `getDb()`. |
| 5 | Rejected writes surface as 500, hiding a security control behind a generic error | Low | `UnknownColumnError` maps to 400 with the column names. |
