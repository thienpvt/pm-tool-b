# Phase 4 Plan 03: Project-Scoped Route Sweep

## Objective

Close the ownership gap across every remaining project-scoped route. Research confirmed **22
project-scoped routes have no session check at all** — this plan gives each one a service that
asserts ownership, following the pattern plan 01 proved on `risks`.

Runs in parallel with plan 04 (disjoint file ownership: this plan owns project sub-resources,
plan 04 owns portfolio/report aggregates).

## Context

After plan 01 the pattern is fixed and mechanical: for each resource, a
`lib/services/<name>.service.ts` wrapping the existing repository with
`assertProjectAccess(projectId, actor)` first, and a route that resolves the session and passes
a plain actor.

Most of these routes are near-trivial pass-throughs — the service adds the assert and nothing
else. That is the point: the assert needs a home, and per CONTEXT that home is the service
layer even when the service is otherwise thin.

**`budget/route.ts` is the exception worth care.** It already has a check
(`checkBudgetAccess`, :14-22) but collapses cross-company to **401**. CONTEXT unifies on 403.
That is a live behavior change and needs an explicit HYG-02 callout — a client branching on
401 will see 403.

<task id="04-03-02" type="tdd">
<action>
Create services for the five structurally richer resources: `bugs`, `holidays`, `milestones`
(including the `[milestoneId]` and `[milestoneId]/epics` sub-routes), `budget`, and `programs`.

`budget.service.ts` absorbs what `checkBudgetAccess` did, plus the existing orchestration:
the three-way `Promise.all` over `listBudgetItems`, `listExpenses`, `activityStats`, the
expense grouping by `Map`, and the `completion_pct` rounding. Move that computation verbatim —
same rounding, same grouping key, same field names. Also move its inline validation
(`!body.name?.trim()` and the CAPEX/OPEX membership test) into the service as `ValidationError`
throws, which the mapper renders as 400 exactly as the route did.

`programs.service.ts` covers `app/api/programs/[id]/route.ts`, which research found unprotected.
Programs map to the `customers` table — scope by the program's company, not a project id, so
this service takes `(programId, actor)` and asserts company ownership against the program row
rather than calling `assertProjectAccess`.

`milestones.service.ts` handles nested ids: assert on the parent `projectId`, and preserve the
existing scoping guard so a milestone from another project cannot be read or mutated through a
matching parent id.

Write tests first, each with a cross-company denial case.
</action>
