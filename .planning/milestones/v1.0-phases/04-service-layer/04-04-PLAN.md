# Phase 4 Plan 04: Aggregates, Reports, and the SVC-05 Proof

## Objective

Extract the orchestration-heavy GET logic from the portfolio and report routes into services
with company-scoped aggregates, and prove the scoping with a real-database cross-company
fixture — SVC-05 explicitly requires proof "rather than by inspection".

Runs in parallel with plan 03; file ownership is disjoint (plan 03 owns project sub-resources,
this plan owns portfolio and report routes).

## Context

Line splits established by research:

| Route | Total | GET logic | POST (AI) |
|---|---|---|---|
| `app/api/portfolio/report/route.ts` | 649 | 33-531 (**499**) | 532-649 |
| `app/api/projects/[id]/project-report/route.ts` | 395 | 33-294 (262) | 295-395 |
| `app/api/projects/[id]/report/route.ts` | 240 | 55-144 (90) | 145-240 |

The POST handlers are ~50 lines of prompt template plus a `createMessage` call against the
Phase 3 client — already correctly factored. CONTEXT locks them **in the route**; moving them
is churn with no security or logic gain.

Two locked constraints carry real risk if forgotten:

1. **`IntegrationError` must propagate untouched.** A service that wraps an Anthropic call and
   catches-and-rewraps would silently undo the Phase 3 behavior freeze — the `force500` split
   and the `validation`-escapes-`force500` rule decided this milestone.
2. **`project-report` GET keeps `companyRagConfig(project.company_id)`** — reading company off
   the project row, not the session. It is arguably the wrong inversion, but changing it is a
   behavior change. Record it, don't fix it.

`app/api/portfolio/route.ts` and `app/api/portfolio/roadmap/route.ts` hand-roll RAG thresholds
inline while the report routes call `lib/rag.ts:calculateRAG`. Extract **as-is**. Reconciling
is a separate HYG-02 commit, not a silent fix inside a refactor.
