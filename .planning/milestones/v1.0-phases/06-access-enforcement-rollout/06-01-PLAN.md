# Phase 6 Plan 01: Substrate — rawBody + Shadow Flag

## Objective

Add the two capabilities every downstream Phase 6 plan depends on, inside the single
`lib/http/with-auth.ts` wrapper that `withProjectAccess` and `withProgramAccess` both delegate
their assert into:

1. **`opts.rawBody: true`** — skip the wrapper's unconditional `req.json()` on POST/PUT/PATCH,
   so multipart/formData upload routes can look at `req` themselves. This unblocks the
   formData routes (`import/resource-plan/[id]`, `export/ppt/[id]`, `parse-file-headers`) in
   plans 06-02 and 06-04.
2. **`ACCESS_ENFORCEMENT` shadow flag** — log-only enforcement mode (ROUTE-08), so the NEW
   denials Phase 6 adds can be observed before enforcement flips on.

Both are wrapper-internal; no behavioral change to any route on its own.

## Context

The wrapper's catch tail today (`with-auth.ts:85-92`): `UnknownColumnError → repoErrorResponse`,
else `serviceErrorResponse`. `serviceErrorResponse` maps ForbiddenError→403, NotFoundError→404,
ValidationError→400, ConflictError→409, else generic 500. The shadow flag must catch ONLY
ForbiddenError/NotFoundError *before* `serviceErrorResponse`.

**Why per-request env read:** `process.env.ACCESS_ENFORCEMENT` must be evaluated on each
request, NOT captured at module load, so the operator flips it at deploy time (set in Railway,
redeploy) without a code change or rebuild.

**Scope of shadow:** this is a GLOBAL flag for the whole process. It is scoped to Phase 6's
new-denial routes by **deploy sequence**, not code — the operator deploys plan 06-02's new
gates with the flag on, confirms no legitimate would-be-denials in the logs, then redeploys
with the flag off (enforcing). The 18 already-enforcing routes would also be under the flag if
it were ever set globally, so the flag MUST be recorded as operator-controlled and short-lived.

<task id="06-01-02" type="tdd">
<action>
Add the `ACCESS_ENFORCEMENT` shadow flag to withAuth's catch tail (`with-auth.ts:87-92`).

Inside the catch, AFTER the `UnknownColumnError` check and BEFORE `serviceErrorResponse`:

```
if (process.env.ACCESS_ENFORCEMENT === 'shadow' && (e instanceof ForbiddenError || e instanceof NotFoundError)) {
  console.error('[ACCESS-SHADOW]', JSON.stringify({ method, path, userId, companyId, errorKind }));
  // fall through to the handler's allow path
}
```

Read `process.env.ACCESS_ENFORCEMENT` per request (inside the wrapper's returned async
function, NOT at module top), so a redeploy toggles it without a rebuild.

Behavior when shadow ON and the error is ForbiddenError/NotFoundError: instead of returning
the 403/404, log the structured line and allow the request — but the handler has ALREADY thrown,
so we cannot re-enter it. The mechanism is: the access wrappers (withProjectAccess/
withProgramAccess) call their assert INSIDE withAuth's try. On shadow, when the assert throws a
ForbiddenError/NotFoundError, withAuth catches it, logs, and must re-invoke the handler WITHOUT
re-running the assert. The cleanest way: withProjectAccess/withProgramAccess expose the assert
as a step the shadow path skips — so on shadow, withAuth logs the denial and calls the handler
with `ctx.project`/`ctx.program` as `undefined` (or the plan passes the assert error to ctx).

**Decide the mechanism explicitly in code and document it:** recommend withAuth gains an
internal `runHandlerAfterDenial(ctx)` path that the access wrappers trigger — on shadow-deny,
log + call the handler with the same ctx but no authorized resource attached.

Structured log line fields: `method` (req.method), `path` (new URL(req.url).pathname),
`userId` (user.id), `companyId` (user.company_id), `errorKind` (e.constructor.name), `targetId`
(the params.id string if present).

Write tests first:
- shadow ON + ForbiddenError → status matches what the handler would return for an authorized
  call (handler invoked), console.error called with a parseable '[ACCESS-SHADOW]' JSON line
- shadow ON + NotFoundError → same allow-through + log
- shadow OFF (unset) + ForbiddenError → 403 via serviceErrorResponse, NO '[ACCESS-SHADOW]' log
- shadow ON + UnknownColumnError → STILL 400 (not allowed through)
- shadow ON + arbitrary Error → STILL 500 via serviceErrorResponse
- env read per-request: flip process.env.ACCESS_ENFORCEMENT between two handler invocations and
  assert both behaviors (proves not hoisted)
</action>
